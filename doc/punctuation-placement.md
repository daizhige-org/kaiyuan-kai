# 标点：接续、位置、半宽压缩、语言 metadata

以下几点均属同一类问题：简中楷将所有标点都当作与汉字相同的满格 1024
单位方块绘制，其位置与宽度都沿用文鼎的旧式排版惯例，与现代简体排版习惯
（尤其是 Word 一类会做"标点挤压"的软件）不符。此处记录最终方案及其原因，
修改 `build.py` 中以下几个函数之前建议先阅读本文档。

## 1. 破折号 / 省略号接续断裂

`fix_repeating_punctuation()`。简中楷原始的 `—`（U+2014）笔画左右均有缩进
（x: 73–952，而非贴边的 0–1024），`…`（U+2026）三个点同样整体缩在
158–867 之间。中文排版中这两个符号习惯连续使用两个、占两个字身
（`——`、`……`），缩进产生的空白会在两个字身的接缝处形成明显断档。

- 破折号：整条线本身即为连续的一整块，直接将轮廓横向拉伸至贴住 0 与
  1024 两条边即可，两个相连后自然是一条不间断的线。
- 省略号：三个点是三个独立轮廓，不能整体拉伸（拉伸会改变比例，六个点的
  间距依旧不均匀）——改为将每个点**平移**至 1024 的六等分点上
  （1/6、3/6、5/6），点的大小保持不变，两个省略号相邻时第三、四个点的
  间距与点内部的间距正好相等。

**曾出现的问题**：仅修改 `glyf` 的轮廓坐标并不充分——fontTools 绘制字形时
实际读取的是 `hmtx` 中的左侧位（LSB），而非重新计算得出的 `glyf.xMin`。
修改轮廓后若未同步更新 `hmtx[gname]` 的 LSB，存盘后重新打开时，笔画会
恢复为修改前的位置（`glyf.xMin` 数值正确，但实际渲染仍是旧位置）——此问题
排查耗时较长，随后整理为 `_set_glyph()` 这一公共工具函数；此后任何直接
修改字形轮廓位置的函数均应调用该函数，不应绕过它直接赋值
`glyf[gname] = ...`。

## 2. 标点纵向位置

`reposition_punctuation_y()`。简中楷将所有标点的墨迹都保留在字身格子内部，
从不越过基线（与其他汉字待遇相同）；现代简体排版习惯是句读符号
（、。，；：！？）明显下沉、部分探至基线以下，引号（“”‘’）则明显
上提、接近字面顶部。

相关数值来自与系统自带 **Kaiti SC**（SinoType，`/System/Library/AssetsV2/.../
Kaiti.ttc`）的实测对比：量出两者每个字符的 y0/y1，按"重心对齐"计算出需要
平移的 dy，再应用到简中楷的轮廓上——**仅作平移，不改动笔画本身**。

## 3. 半宽标点压缩：`halt` 特性，而非改动默认字形

最初采用的是"直接收窄默认字形"的方案（将引号 advance 从 1024 直接改为
404/248），效果虽然正确，但方向并不合适：**中文字体的默认值理应是满格
等宽的**，压缩应当是排版软件"可选启用"的行为，而不应固化为字体的默认
表现。两者的区别在于：

- 满格默认：任何软件、任何场景下，一个汉字/标点都占一格，适合表格、对齐、
  不具备 CJK 排版智能的场合，是最安全、兼容性最广的默认值。
- 压缩为可选特性：只有明确支持并请求 OpenType `halt`（Alternate Half
  Widths）的软件（Word 的"标点挤压"、InDesign 等）才会使标点收窄并贴紧
  前后文字；不支持的软件仍显示满格默认，不会出错。

相关数值并非主观设定，而是从 `/System/Library/Fonts/Hiragino Sans GB.ttc`
（苹果为简体中文提供的系统字体，本身即带有 `halt`）中实测得到的真实 GPOS
表，其规则十分统一：

- 每个标点：`XAdvance = -unitsPerEm/2`（去掉右半个字身）。
- "开"标点（“ ‘ （ 《 「 『 【 〔 〈）额外附加 `XPlacement =
  -unitsPerEm/2`（整体左移半格，贴住后一个字）。
- "闭"标点（” ’ ）》」』】〕〉）与自由符号（、。，；：！？）无需移位，
  仅需去掉宽度。

按 Hiragino 的 upm=1000 换算至本项目的 upm=1024，即统一为 `±512`。使用
`fontTools.feaLib`（官方 FEA 编译器，而非此前存在缺陷的
`fontTools.merge`）现场编写并编译出一张干净的 GPOS 表，并以 `hb-shape`
验证：默认状态下全部为 1024，启用 `+halt` 后标点变为 512（开标点另带
-512 位移），汉字则完全不受影响。

详见 `add_halt_feature()`。

## 4. `meta` 表：`dlng`/`slng`

简中楷、UKai 两个上游字体均没有 `meta` 表。系统中文字体（Kaiti SC、
Hiragino Sans GB）均使用 `meta.dlng`（Design Languages）声明"该字体是为
何种语言设计的"——均为 `zh-Hans`，这比 Font Book 从 `OS/2 ulUnicodeRange`
位反推出的"支持语言"列表准确得多、也简短得多（本项目的 `ulUnicodeRange`
因合并了 UKai 的希腊/西里尔/假名/注音字符，反推出的语言列表异常冗长，
但这些字符只是"附带覆盖"，并非该字体真正的设计目标）。

`meta.slng`（Supported Languages）则相反：应如实反映"该字体的字符集实际
能够覆盖哪些语言"，既不能主观臆造，也不能照搬参考字体的清单。使用
[hyperglot](https://github.com/rosettatype/hyperglot)（专门用于检测字体
正字法支持情况的工具）对最终的 cmap 进行检测，得到 373 种语言（360 种
拉丁、7 种西里尔、7 种中文变体），每个 ISO 639-3 代码用 `pycountry` 换算
为 639-1（能换算则换算，无法换算则保留三字母，与参考字体列表中 `yue`、
`tok`、`jbo` 一类写法一致），另外手动补充了 `zh`、`zh-Hans`（hyperglot 是
按官话/粤语/吴语等具体语言变体分别报告的，没有笼统的"中文"标签）。

结果固定写入 `build.py` 的 `_SLNG` 常量中（并附有重新生成所需的命令注
释）——`hyperglot`/`pycountry` 并未加入 `build.py` 的运行依赖，这两个包
仅在需要重新核算语言覆盖范围时手动安装并运行一次。

详见 `set_meta_languages()`。

## 排查方法论（延续 word-line-spacing.md 的风格）

1. **先寻找参照对象，避免主观猜测数值**——无论是行高、标点位置还是标点
   压缩比例，本次改动均未凭经验判断而定，而是从"确认工作正常"的系统
   字体（Kaiti SC、Hiragino Sans GB）中实测取得，并按 unitsPerEm 比例
   换算而来。
2. **区分"默认行为"与"可选特性"**——默认值应照顾最广泛、不具备 CJK 排版
   智能的场景（满格等宽）；只有在明确具备检测/请求能力的场景下，才应
   呈现压缩效果（`halt`）。将可选特性固化进默认字形，是此次走过的一段
   弯路。
3. **修改轮廓位置时，`glyf` 与 `hmtx` 需一并调整**——仅修改其一，存盘
   重新打开后会出现"坐标正确但渲染不正确"的现象（详见第 1 节破折号/
   省略号部分的教训）。
4. **实测所得的数值应可验证**——`hb-shape --features="+halt"` 一类命令行
   工具可直接验证 OpenType 特性是否确实按预期工作，不应仅凭肉眼观察渲染
   结果。
